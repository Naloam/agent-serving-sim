# Agent 负载下的 KV Cache 模拟器（二）：真实 trace 采集、两个数据管线的坑、一份负载刻画

系列第二篇，对应里程碑 M2。上一篇的结论建立在合成负载上，而合成负载的每个"合理假设"都可能是结论翻转的开关：think_time 的分布形状、前缀各段的占比、轮长的增长方式，都直接影响"TTL 设多少最优"这类答案。文献里的论文几乎都不放 trace，社区反复在问有没有公开的 agent serving trace。所以 M2 只干一件事：在本机把真实流量跑出来、记下来、刻画清楚。

## 采集系统：一个探针、两类假 agent、一块 4060

探针是三百行标准库，一个 OpenAI 兼容的记录代理。agent 把 base_url 指向它，它原样转发给上游，响应逐字节透传，绝不阻塞请求；同时在响应结束后把每个请求的原始事实追加写进 JSONL——三个墙钟时间戳（到达、首字节、完成），两个自定义头带进来的会话与类型标识，原始 messages 和上游返回的精确 token 数。

探针只记事实，不做解释。所有清洗对齐留给离线的 loader。这个分层在后面救了我们，原因等会讲。

驱动器不是简单的请求回放。两类 agent（模型用 qwen2.5-coder-7b，Ollama 服务在 4060 上）跑的是真实的工具调用回路：coding agent 的系统提示词描述一个 Python 仓库，配 run_tests、read_file、write_file 三个工具，模型真的会发起工具调用，驱动器返回合成的工具结果——测试输出、文件内容——把对话滚下去。search agent 配 web_search，返回合成的 SERP 摘要，摘要进入历史，prompt 逐轮膨胀。轮间空闲用真实 sleep 模拟 agent 侧处理，coding 中位数五秒，search 中位数二十秒。会话按泊松过程错峰启动，四路并发抢同一块 GPU，排队效应被真实地记进时间戳里。

部署上有个细节值得一提：Ollama 的 OpenAI 端点不接受 num_ctx，默认 4096，会静默截断长会话的前缀——对前缀复用研究是致命的。解法是用本地 blob 派生一个 16K 上下文的模型变体，零下载。

两批共采了 1021 个请求、162 个会话，墙钟约 70 分钟。

## 坑一：逐请求独立估算 token，前缀悄悄断了

原始日志不等于 trace。把 OpenAI 消息流转成"四段前缀分解加轮间空闲"的结构化数据时，第一版 loader 对每个请求按各段字符占比独立分摊 token 数。

这个做法看起来无害，直到重放实验里命中率只有 0.42——理论上限接近 0.99。排查了一阵才发现：同一段 system prompt 在不同轮的估算值会差几个 token，126、132、125 这样跳。对模拟器而言这等于"每轮的 system prompt 都不一样"，radix tree 上对话流永远接不上。

修复是把逐请求估算改成累计记账：前导（system 加 tools）按类型在第一个请求上估出来之后固定；对话流按 history(t+1) = history(t) + new(t) + output(t) 累计，output 取上游真实返回的 completion_tokens，new 用总量减出来当残差，吸收噪声。改完命中率回到 0.9855。

这个坑最阴险的地方在于它不报错。每个请求的估算都"对"，跨请求的一致性碎了，而前缀复用恰恰只关心跨请求的一致性。

## 坑二：一个预热请求污染了整个类型

修完第一个坑，重放命中率回来了，但 coding 类的前导占比变成了 0。追下去发现是采集脚本启动时的一个预热请求：没有会话头，被默认归类成 coding，而它没有 system 段——整个 coding 类型的前导估计被它定型成了零。

修复很小，只有带会话标识的请求才有资格定型类型参数，匿名请求退回逐请求拆分。但两个坑合起来给了一条教训：凡是"按内容估算再下游对齐"的管线，都要显式维护跨请求的一致性不变量，并且用不变量写断言。我们补了 history 累计关系的单测。

## 一份真实负载长什么样

修复后的数字（`traces/real/REPORT.md`，`python experiments/analyze_real_trace.py` 可复现）：

| 指标 | coding | search |
|------|--------|--------|
| 请求 / 会话 | 702 / 100（平均 7.0 轮） | 319 / 62（平均 5.1 轮） |
| think_time 中位数 | 5.8 s | 19.3 s |
| think_time p95 | 14.7 s | 57.2 s |
| 对数正态拟合 | μ=1.75, σ=0.56 | μ=2.92, σ=0.72 |
| prompt 均值 | 1182 tok | 503 tok |
| 前导占比 | 29% | 37% |
| 历史占比 | 62% | 59% |
| 逐轮增长 | 366 → 2882 tok（14 轮） | 208 → 1313 tok（10 轮） |

三个刻画结论。轮间空闲是双峰的，类间差 3.3 倍，各自良好服从对数正态——"TTL 应当设在两类回转周期之间"这个直觉第一次有了参数依据。历史是 prompt 的主体，占六成且逐轮近线性增长，agent 负载的 KV 压力主要来自会话自身的历史累积。前导占三成左右：跨会话可共享的部分不可忽略但不是大头，纯 preamble 缓存的天花板有限。

## 计时标定：能标到什么程度就说到什么程度

用 1021 个请求做最小二乘，得到 prefill 大约 3913 tok/s、decode 51.8 tok/s、固定开销 2.7 秒，R² 只有 0.32。decode 速率和 4060 上 7B-q4 的公开实测吻合，但 R² 这么低的原因必须老实说：总时延里混着四路并发下 Ollama 内部的排队，而排队和自身 token 数弱相关。非流式采集只能标定到这个精度；要分解 TTFT 和排队，需要流式首 token 时间戳（探针支持，留作下一轮，后来做了，见第四篇）。

## 用真实 trace 重放策略实验

把清洗后的请求按原始到达时间重放进模拟器，扫 TTL：LRU 命中率 0.9855，接近理论上限；TTL 从 1.9 秒扫到 29.6 秒，命中率单调逼近 LRU。上一篇的结构性结论在真实负载上复现了。

另一个诚实的发现：这份采集负载（约四路并发会话）的活跃工作集远小于 60K token，60K 和 200K 容量的重放结果逐位相同。容量压力场景需要更高并发或更小显存——这正是合成实验的价值所在。

数据在 `traces/real/`：两个类的 JSONL trace、4.8 MB 原始日志、刻画报告、标定文件。复现一条龙：`collect_real_trace.py` 采集，`analyze_real_trace.py` 刻画入库，`exp005_real_trace_replay.py` 重放。
