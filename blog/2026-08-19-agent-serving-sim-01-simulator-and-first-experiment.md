# Agent 负载下的 KV Cache 模拟器（一）：设计、实现与第一组实验

这是系列第一篇。项目目标一句话：一个开源、可复现的 LLM agent 负载推理服务模拟器——trace 进，模拟 KV cache / 调度 / 淘汰策略，JCT、命中率、显存曲线出。代码在 https://github.com/Naloam/agent-serving-sim ，本篇所有数字可以用 `python experiments/exp001_lru_vs_ttl.py --seed 42` 复现。

## agent 负载和聊天负载不是一种负载

2025 年之后，推理服务的请求来源正在从"人"变成"agent"。这件事对 KV cache 管理的影响比多数人直觉的大。

一个 coding agent 跑一个任务动辄几十轮调用。轮和轮之间，agent 在跑测试、读文件、调搜索——请求间隔从几秒到几百秒不等。同一 agent 的所有请求共享同一段 system prompt 加工具定义，几 KB 到几十 KB，逐字节相同。第 N 轮的 prompt 等于前导加上前 N-1 轮的全部对话，而这段前缀恰好是上一轮刚算完的 KV。

SGLang 的 RadixAttention 用 radix tree 组织前缀缓存，解决了"能不能复用"。没解决好的是"留还是不留"：留着，下一轮命中，省一次全量 prefill；不留，显存被长空闲会话占着，挤压别人。TTL（Continuum/CacheTTL）、优先级驱逐（TensorRT-LLM）、多 agent 配额（TokenCake）都是对这个问题的回答，但这些工作的模拟器和 trace 基本都不开源，复现和横向对比很困难。

所以我写了这个模拟器。CPU 上跑，纯 Python，10 万请求 19 秒，希望成为这个方向的公共基线。

## 三个设计决定

事件循环是自研的，没用 simpy。heapq 优先队列加上惰性取消，一百多行，换来对调度语义的完全掌控。事件按 (时间, 优先级、入队序) 排，同一时刻的行为完全确定。仿真里的时间是虚拟的，测试不需要 sleep。

第二个决定花的心思最多：radix tree 的元素不是 token，是"段"。

FR 要求树支持共享前缀分裂和引用计数保护，这需要真实的前缀语义。但 10 万请求乘上平均 4K token 的逐 token 操作，纯 Python 跑不完。观察是：agent 负载的前缀共享天然分段——同一 agent 类型的所有请求共享同一段前导（system prompt 加工具定义），会话的对话流按位置对齐逐轮增长。于是树的元素定义成 `Segment(stream, length)`：同一条流的任意短段是长段的前缀，不同流在交界处分叉。每个请求只有两个段，树的全部语义——分裂、部分命中、引用保护——和 token 级同构，复杂度却和 token 数无关。

后来对照 SGLang 的 `radix_cache.py` 读源码，它的 `_split_node`、lock_ref、只逐叶子的语义在这个抽象下都能一一对应。写模拟器附赠的理解红利，算意外收获。

第三个决定是不模拟真实计算。prefill 时间等于未命中 token 数除以吞吐，decode 同理。模拟器定位是策略相对收益对比，不是绝对性能预测，吞吐参数后面用真实服务标定。驱逐策略做成可插拔的，统一接口，新策略一个类加一个注册点，不动内核。

## 一个踩掉的方法论坑

最初我把 TTL 实现成"缺空间时优先淘汰过期条目，LRU 兜底"。写完推演了一遍，发现不对：过期集恰好是按最近访问排序的尾部，这种"排序式 TTL"的受害者集合和纯 LRU 完全一样，TTL 扫描实验会得到一条平线。

正确的语义必须是主动清除：条目距上次访问超过 TTL 就从树里移走，之后到达的请求不能再命中它。TTL 和 LRU 从此才真正分道扬镳。

## exp001：同构负载下的 LRU vs TTL

设置：300 会话乘 8 轮共 2400 请求，会话泊松到达，think_time 对数正态（中位数 7.4 秒），缓存 100K token，并发上限 8。同一份 trace 分别跑 LRU 和五档 TTL。

| policy | hit_rate | JCT mean (s) | JCT p95 (s) | 驱逐次数 | TTL 清除 token |
|--------|----------|--------------|-------------|----------|----------------|
| lru    | 0.813    | 10.05        | 24.69       | 2308     | —              |
| ttl-5  | 0.549    | 22.31        | 45.74       | 0        | 4.85M          |
| ttl-10 | 0.719    | 13.56        | 30.59       | 88       | 3.19M          |
| ttl-20 | 0.804    | 10.06        | 24.69       | 1913     | 0.46M          |
| ttl-40 | 0.813    | 10.05        | 24.69       | 2282     | 0.10M          |
| ttl-80 | 0.813    | 10.05        | 24.69       | 2308     | 0.03M          |

TTL 单调趋近 LRU，且始终不超过它。TTL 设 5 秒（小于轮间隔中位数）时命中率掉到 0.55、JCT 翻倍；80 秒时和 LRU 完全一致。

这不是 bug，是这种负载下的结构性结论。think_time 同分布时，"过期集 ⊆ LRU 尾部"意味着 TTL 只会额外放弃 LRU 本可保留的命中——晚归会话的迟到重命中——换不来任何收益。那文献里"TTL 存在最优值"从哪来？来自异构：不同 agent 的轮间隔分布不同时，设置得当的 TTL 能把长间隔会话的死缓存及时让给短间隔会话。这是 M3 要验证的命题，也是优先级驱逐和配额的同一动机。
